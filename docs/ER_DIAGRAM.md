### Relationships

| Relationship | Cardinality | Description |
|---|---|---|
| users → projects | 1 : many | A user owns many projects |
| projects → tasks | 1 : many | A project contains many tasks |
| users → tasks | 1 : many | Denormalised ownership shortcut |

### Why `userId` is on `tasks`

Tasks store both `projectId` (parent) and `userId` (owner) as a **denormalised ownership shortcut**.

This allows every task authorisation check to be a single-table query:
```sql
SELECT * FROM tasks WHERE id = ? AND userId = ?
```

Without this, every check would require a join through `projects` to verify ownership — adding complexity and a small performance cost with no security benefit.

## Cascade Behaviour

| Action | Effect |
|--------|--------|
| Delete user | All their projects and tasks are deleted |
| Delete project | All tasks under that project are deleted |

This is enforced at the database level via `ON DELETE CASCADE` foreign keys, generated by Prisma.
